# Design notes

## Goals

1. Notes are plain files. Shared notes are reviewed and committed with the code; private notes never enter
   the repository.
2. The format is portable. Everything on disk is documented in `spec/FORMAT.md` and pinned by generated
   fixtures, so a second IDE can read and write the same folders.
3. Private data stays private. No telemetry, no servers; sensitive notes never leave the machine and AI
   tools can only *send* content into Folium, never read it.
4. Fast enough for real projects: 5,000 notes load in a few seconds, edits settle in ~0.2 s and search
   runs in tens of milliseconds.

## Layers

```
src/
  core/      pure TypeScript, no VS Code API (format, search, tasks, links, templates, crypto, import/export)
  store/     filesystem: scan, personal state, trash, renames, overlays, indexes, backup
  ui/        views, editor features, virtual FS, status bar, search UI
  commands/  one module per area; ids match src/manifest/contributions.ts
  manifest/  package.json contributions, generated by scripts/gen-contributions.mjs
  mcp/       standalone stdio MCP server (separate esbuild bundle)
  git.ts     git remotes/branch/user and `.git/HEAD` polling
  app.ts     lifecycle: settings, store rebuilds, watchers, refresh batching, context keys
```

`core` is the shared specification: it is unit tested directly and it generates `spec/fixtures`. Nothing
in `core` imports `vscode`, so the same logic can power a JetBrains plugin or a test harness.

## Data flow

```
fs ──scan/read──▶ store (NoteSummary + raw + personal state)
                     │
                     ├─▶ SearchIndex (title/tag/body weights, typo tolerance)
                     ├─▶ LinkIndex (wiki links, backlinks)
                     ├─▶ tasks (parsed lazily from raw)
                     └─▶ views (filters → grouping → sorting)

text editor ──unsaved buffer──▶ overlay (store reflects unsaved edits immediately)
file watcher ──external change──▶ debounced refresh (120 ms)
```

Writes go through a per-file promise queue. Front-matter edits replace only the field being changed
(`setFrontMatterField`), so unrelated lines, comments and custom keys keep their exact bytes. Renames move
personal state to the new key and rewrite wiki links when enabled.

## Performance

* Scan is parallel (32 concurrent reads) and only reads `.md` files below the two roots.
* **Refreshes are incremental**: the directory walk is followed by a `stat` per file, and unchanged notes
  (same mtime/size, no unsaved overlay) reuse the existing parsed object. One external edit therefore
  costs a walk + stats + one parse instead of re-reading and re-parsing 5,000 notes.
* Per-note task and tag caches are primed during the scan and reused by the indexer, so no note is parsed
  twice per change; `tagCounts()`/`tasks` are O(1) reads of the cached values.
* Search keeps per-note lower-cased title/body and token lists, reusing entries whose `mtime:size:title`
  signature is unchanged. Fuzzy matching only runs when substring/prefix matching fails.
* Views memoize filtered notes/groups per refresh and compute grouping from the already-filtered array.
* Measured on the development machine (Linux, Node 26, 5,000 generated notes):
  cold load + index **≈1.7 s**, search **16–45 ms**, cached tags/tasks **≈0 ms**, refresh with no changes
  **≈150 ms**, refresh after one external edit **≈150 ms**, note creation **≈35 ms**. Before incremental
  refresh the same refresh took **≈1.3 s**. The VS Code extension-host perf phase measures
  **refresh 164 ms, search 29 ms, create 28 ms** for the same 5,000 notes.
* `test/perf/store.test.ts` prints these numbers on every run and asserts generous upper bounds so it
  fails only on real regressions.

## Format decisions

* **ULID** ids: sortable, no coordination, 26 characters.
* **Local ISO with offset**: human readable, keeps the author's timezone, no milliseconds.
* **`endText`**: a snippet's first three lines are not enough to grow a range; the last line anchors the
  end.
* **Personal state keyed by id**: survives renames; falls back to `scope:relPath` for hand-written notes
  without ids.
* **Trash inside the private folder**: shared notes can be restored without polluting the repository, and a
  shared clone never sees another developer's trash.
* **`Folium-encrypted` fence** instead of a binary format: diffs stay readable in structure, the title line
  and header remain available for the tree view, and the payload is standard AES-256-GCM.

## Security

* `capabilities.untrustedWorkspaces: limited`: project settings that could redirect tokens or commands
  (issue URLs, custom prompt command) are ignored in untrusted workspaces; encryption settings are
  user-level.
* Tokens live in `SecretStorage`. Issue requests check the destination host; unknown hosts require an
  explicit confirmation.
* Sensitive/encrypted notes are filtered out of export, Joplin sync, issue creation and every AI path.
* AI inbox requests are capped at 200 KB, written with temp-file + rename, and claimed by atomic rename so
  two IDEs cannot both consume one request.
* The MCP server exposes exactly one tool; it never reads notes.

## Testing

* **Unit (Vitest)**: format round-trips, byte-preserving edits, project keys, file names, tags, tasks,
  crypto vectors, tar/backup, search ranking, code-link resolution, wiki links, templates, importers,
  exporters, follow-ups, views, store behaviour on real temporary folders, manifest consistency, the
  bundled extension smoke test and the MCP server protocol. A dedicated file simulates Windows with
  `path.win32` (drive letters, reserved names, case-insensitive collisions).
* **Performance**: a 5,000-note test asserts load/search/group/task timings.
* **Integration (`@vscode/test-electron`)**: real extension host, real files: create/open/search, private
  paths, tasks, encryption key, then a second launch that verifies notes, colors, pins and (where the OS
  keyring is persistent) the secret key survive a restart, then a 5,000-note performance phase. Run with
  `VSCODE_EXECUTABLE=/path/to/code npm run test:integration` to reuse an installed VS Code.
* **Fixtures**: `npm run fixtures` regenerates `spec/`; `npm run fixtures:check` fails CI when stale.

## Known limitations

* Only the VS Code extension is implemented here. The JetBrains plugin is expected to implement
  `spec/FORMAT.md`; the companion zip ships the spec, fixtures, templates and the MCP server for that work.
* The VS Code integration tests need a graphical session (use `xvfb-run` on headless Linux). On Linux
  without a keyring, SecretStorage is per-window, so the restart test skips only the key-persistence
  assertion (verified by a canary secret) and still checks notes, colors and pins.
* Screenshots for the marketplace are generated previews (`images/walkthrough-*.svg`); real screenshots
  must be captured on Windows/macOS before publishing (see `docs/publishing-checklist.md`).
